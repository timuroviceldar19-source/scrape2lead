# Техническое задание (ТЗ)

## Разработка платформы сбора и обогащения B2B-данных с MVP-адаптером 2GIS

**Проект:** Scrape2Lead v1.7
**Стек:** Node.js, TypeScript, Playwright

---

## 1. Общие сведения и назначение системы

Настоящее техническое задание определяет требования к проектированию, разработке и тестированию программного комплекса **Scrape2Lead**.

Система предназначена для автоматического сбора актуальной контактной информации юридических лиц и индивидуальных предпринимателей из разных источников данных. В рамках первой поставки реализуется только **2GIS Adapter** как тестовый полигон платформенной архитектуры.

Основная цель проекта — генерация B2B-базы лидов по заданным географическим локациям и отраслевым категориям с устойчивостью к изменениям интерфейса источников, системам защиты от ботов и возможностью подключения новых Source Adapter без изменения ядра.

> **Замечание об устойчивости:** система зависит от структуры DOM и CSS-селекторов 2GIS, которые меняются без предупреждения. Поддержание парсера в рабочем состоянии — это постоянная задача, а не разовая разработка. Поломка из-за изменений на стороне 2GIS считается работой по поддержке, а не дефектом (см. п. 7).

## 0. Объём первой поставки (MVP Scope)

Первая поставка фиксируется как **ядро платформы + один рабочий адаптер 2GIS**. Остальные источники и продуктовые слои описаны как архитектурный задел, но не входят в стоимость и критерии первой поставки. Да, это скучно, зато спасает от сметы размером с небольшой космодром.

**Входит в MVP:**

- Core Platform: Job Manager, Queue / Scheduler, Worker Pool.
- Source Adapter Layer и контракт `ISourceAdapter`.
- Один реализованный адаптер: `2gis`.
- Browser Session Manager: запуск, перезапуск, прокси, fingerprint-патчи, watchdog.
- Parser Core через методы адаптера: API Capture / DOM Fallback.
- Storage Layer на SQLite (`better-sqlite3`) с миграциями.
- Унифицированная модель `Lead` (`source + external_id`).
- Normalizer: телефон, email, URL, соцсети, флаг неполноты, дедуп.
- Retry / Backoff, Rate Limiter, Telemetry, Logging, Raw Data Storage.
- Экспорт XLSX/CSV.
- Юнит-тесты, контрактный тест адаптера, E2E на сохранённых HTML/JSON-снимках 2GIS.

**Не входит в MVP и реализуется отдельными этапами:**

- Google Maps Adapter.
- Yandex Maps Adapter.
- Avito Adapter.
- HH Adapter.
- Полноценный Custom Website Adapter как самостоятельный источник.
- Lead Scoring.
- CRM Integration / CRM Export Layer.
- Analytics Dashboard.
- Multi-source Aggregation между несколькими источниками.
- Внешний CAPTCHA solver, если не согласован отдельно.

**Правило приоритета:** если старые разделы ТЗ противоречат разделу 8 или этому MVP Scope, приоритет имеют раздел 8 и раздел 0.

### 2.1. Дорожная карта антибот-маскировки

Реализуется на Этапе 2. Цель — закрыть «я сделал stealth, но он 60% на creepjs» заранее.

**Патчим отпечатки:**
- `navigator.webdriver` — убрать.

**Детект-тесты и целевой скор (критерий приёмки Этапа 2):**
- `bot.sannysoft.com` — все проверки зелёные.
- `creepjs` — без явных red-флагов автоматизации, trust-скор в «человеческом» диапазоне.
- `browserleaks.com` (canvas/webgl/webrtc) — без утечки реального IP и без автоматизированных аномалий.

Если конкретный скор не достигнут — фиксируется как известное ограничение с оценкой доработки, а не «сделано».

## 3. Архитектурная структура и логика работы

Модульная консольная утилита CLI или локальный веб-сервис, разделённая на ключевые компоненты.

### 3.1. Модуль инициализации и конфигурации

Параметры через `config.json` или аргументы CLI:

- `geo` — целевой город или список, например: `Москва`, `Санкт-Петербург`.
- `category` — рубрика, например: `Автосервисы`, `Стоматологии`.
- `proxy_api_url` — ссылка на смену IP прокси.
- `delay_range` — диапазон задержки между действиями, например: `[2000, 5000]` мс.
- `rotate_every_n` — число карточек до ротации IP (см. п. 4.2).

Конфиг валидируется через **Zod** при старте: опечатка в `proxy_api_url` или неверный тип `delay_range` должны падать сразу с понятной ошибкой, а не через час работы.

### 3.2. Модуль эмуляции браузера и сбора данных (Parser Core)

**Приоритет источника данных: внутренний API 2GIS, не DOM.** Список и детали карточек 2GIS грузятся через XHR/GraphQL. DOM меняют почти еженедельно, а эндпоинты живут месяцами. Поэтому:

1. Инициализирует изолированный контекст Chromium со stealth-маскировкой.
2. Подключает резидентный/мобильный прокси.
3. Переходит по базовому URL поиска 2GIS с подстановкой города и категории.
4. **Перехватывает JSON-ответы** через `page.on('response')` (модуль `api-capture`) — основной источник данных.
5. Реализует бесконечный скроллинг левой панели до полной прогрузки списка (триггерит подгрузку XHR).
6. Кликает по карточке для открытия деталей; данные берёт из перехваченного JSON.
7. **Fallback на DOM-парсинг**, если нужный JSON не пойман — после появления целевых селекторов (динамическое ожидание).

> **Требование к сбору контактов:** скрипт обязан эмулировать клик по кнопкам `Показать телефоны`, `Показать контакты`, если они скрыты под спойлером — без клика данные не подгружаются (ни в DOM, ни в XHR).

### 3.3. Обработка CAPTCHA (новое, обязательно)

2GIS показывает CAPTCHA при подозрительной активности. Скрипт должен:

1. Детектировать появление CAPTCHA по селектору/признаку.
2. По умолчанию — приостановить поток, сменить IP и повторить сессию.
3. (Опционально, по согласованию) интеграция с внешним решателем — оценивается отдельно по стоимости и сроку.

При невозможности обойти CAPTCHA поток помечается как заблокированный и логируется, без падения всей системы.

### 3.4. Job Manager / Queue Layer

Управляет очередью работ и распределением между воркерами. Очередь хранится в БД (SQLite для MVP), что даёт переживание перезапуска без потери прогресса.

**Два уровня задач:**

- `parse_jobs` — задача верхнего уровня: одна пара `(city, category)`. Создаётся при запуске сессии.
- `company_tasks` — задача на одну карточку компании (`source + external_id`). Порождается из `parse_job` после сбора списка компаний.

**Статусы задач:** см. State Machine (п.3.5).

**Распределение между воркерами:**

- Воркер атомарно «забирает» задачу: `UPDATE ... SET status='processing', worker_id=?, lease_until=? WHERE status IN ('pending','retry_scheduled') AND (lease_until IS NULL OR lease_until < now) LIMIT 1` (claim через транзакцию / `BEGIN IMMEDIATE` в SQLite).
- `lease_until` — аренда задачи. Если воркер не завершил задачу в срок аренды, задача считается «зависшей» и доступна для перезахвата.
- Один `company_task` обрабатывается строго одним воркером в момент времени.

**Восстановление после падения:**

- При старте Job Manager сбрасывает «осиротевшие» задачи: `processing` с истёкшим `lease_until` → `retry_scheduled`.
- `parse_job` продолжается с места: уже собранные `company_tasks` в статусе `success`/`partial` повторно не создаются и не обрабатываются.

**Защита от повторной обработки одной карточки:**

- `UNIQUE(source, external_id, parse_job_id)` в `company_tasks`.
- Перед записью результата — проверка текущего статуса карточки; переход в терминальный статус идемпотентен.
- Дедуп на уровне данных — по `source + external_id` и нормализованному телефону (п.4.4).

### 3.5. State Machine

Единая модель состояний для `company_tasks` (и применимо к `parse_jobs`).

**Состояния:**

| Статус | Значение |
|---|---|
| `pending` | Задача создана, ждёт воркера. |
| `processing` | Захвачена воркером, выполняется. |
| `success` | Карточка собрана полностью. Терминальный. |
| `partial` | Карточка собрана частично (нет части полей, спойлер не раскрылся). Терминальный (с флагом неполноты). |
| `failed` | Исчерпаны попытки или невосстановимая ошибка. Терминальный. |
| `blocked` | Получен бан/CAPTCHA, требует ротации IP. Промежуточный. |
| `retry_scheduled` | Запланирован повтор с backoff (см. п.3.8). |

**Правила переходов:**

- `pending → processing` — захват воркером.
- `processing → success` — все обязательные поля собраны.
- `processing → partial` — собрано частично, но повтор смысла не имеет (данных в источнике нет).
- `processing → retry_scheduled` — временная ошибка (таймаут, сетевая ошибка, не раскрылся спойлер при наличии признака данных), попытки не исчерпаны.
- `processing → blocked` — `403/429`/CAPTCHA. Триггерит ротацию IP; после ротации `blocked → retry_scheduled`.
- `retry_scheduled → processing` — наступил срок повтора, задача захвачена.
- `processing → failed` — исчерпан лимит попыток или невосстановимая ошибка (например, карточка удалена).
- Любой `processing` с истёкшей арендой → `retry_scheduled` (восстановление, п.3.4).

Терминальные состояния (`success`, `partial`, `failed`) не переходят дальше. Каждый переход логируется и увеличивает соответствующий счётчик метрик (п.3.9), запись попытки идёт в `parse_attempts` (п.3.7).

### 3.6. Browser Session Manager

Отделён от Parser Core. Parser Core получает готовую страницу и не знает о прокси, патчах и перезапусках.

**Зона ответственности:**

- Запуск Chromium (headless/headful, флаги).
- Создание и пересоздание контекста браузера (`browserContext`).
- Смена прокси: новый контекст с новым прокси-каналом (прокси задаётся при создании контекста — см. п.4.2).
- Применение fingerprint-патчей при создании контекста (состав — п.2.1).
- Очистка cookies/session (новый контекст = чистая сессия; обнуление лимитов 2GIS — п.4.2).
- Контроль зависаний: watchdog по таймауту операции → пометка контекста как нездорового.
- Контроль утечек памяти: мониторинг RSS процесса; при превышении порога (п.5.2) — корректное закрытие и пересоздание инстанса.

**Интерфейс (концептуально):** `acquirePage()`, `recycleContext(reason)`, `rotateProxy()`, `dispose()`. Voркер запрашивает страницу у Session Manager и возвращает её; пересоздание — прозрачно для логики парсинга.

### 3.7. Storage Layer

Единый слой доступа к БД. **MVP: SQLite (better-sqlite3).**

**Ограничения SQLite и путь миграции:**

- Один writer: при многопоточности конкурентная запись сериализуется (WAL-режим смягчает, но не снимает). При большом числе воркеров — узкое место.
- Нет сетевого доступа: воркеры обязаны быть в одном процессе/хосте.
- Слабая конкурентность на запись под высокой нагрузкой.
- **Путь миграции на PostgreSQL:** доступ к БД инкапсулирован в Storage Layer (репозитории), SQL держать совместимым; миграции через `drizzle-orm`/`umzug`. Переход при >3–4 параллельных воркерах, распределённом запуске или необходимости конкурентных писателей. Схема таблиц ниже совместима с обеими СУБД.

**Таблицы:**

`parse_jobs` — задача верхнего уровня (город+категория).
- `id` (PK), `city`, `category`, `status`, `total_found` (int), `created_at`, `updated_at`, `finished_at`.

`companies` — итоговые лиды (дедуп-сущность).
- `id` (PK), `source`, `external_id`, `company_name`, `category`, `city`, `address`, `phones` (JSON/text), `email`, `website`, `social_links` (JSON/text), `messenger_links` (JSON/text), `is_partial` (bool), `parsed_at`. `UNIQUE(source, external_id)`.

`company_tasks` — задача на карточку (рабочая единица очереди).
- `id` (PK), `parse_job_id` (FK), `source`, `external_id`, `status`, `attempts` (int), `next_run_at`, `worker_id`, `lease_until`, `last_error`, `created_at`, `updated_at`. `UNIQUE(source, external_id, parse_job_id)`.

`parse_attempts` — журнал попыток (аудит и метрики).
- `id` (PK), `company_task_id` (FK), `attempt_no`, `result` (`success`/`partial`/`failed`/`blocked`/`error`), `error_type`, `proxy_id`, `duration_ms`, `created_at`.

`proxy_history` — история использования и ротаций IP.
- `id` (PK), `proxy_channel`, `ip` (nullable), `rotated_at`, `reason` (`N_cards`/`403`/`429`/`captcha`/`manual`), `cards_on_ip` (int).

`captcha_events` — фиксация CAPTCHA.
- `id` (PK), `company_task_id` (FK, nullable), `proxy_id`, `captcha_type`, `resolution` (`rotated`/`solved`/`skipped`), `snapshot_id` (FK на `raw_snapshots`), `created_at`.

`raw_snapshots` — сырые данные (см. п.3.11).
- `id` (PK), `company_task_id` (FK, nullable), `kind` (`json`/`html`), `purpose` (`error`/`captcha`/`fixture`/`recent`), `payload` (text/BLOB или путь к файлу), `created_at`.

### 3.8. Retry / Backoff Policy

- **Попыток на карточку:** по умолчанию `max_attempts = 3` (настраивается).
- **Ретраятся** (→ `retry_scheduled`): таймаут навигации, сетевая ошибка, временно не найден целевой JSON/селектор при признаке наличия данных, разрыв из-за пересоздания контекста.
- **Не ретраятся** (→ `failed` сразу): карточка не существует/удалена, невалидный `source + external_id`. (→ `partial`): данных нет в источнике.
- **Карточка → `failed`:** исчерпан `max_attempts` либо невосстановимая ошибка.
- **Смена прокси:** при `403/429`/CAPTCHA (статус `blocked`), а также по счётчику `N` карточек на IP (п.4.2). Ротация не тратит попытку карточки, если бан не связан с самой карточкой.
- **Перезапуск браузера:** при превышении лимита RAM (п.5.2), зависании (watchdog), фатальной ошибке контекста. Текущая задача → `retry_scheduled`.
- **Backoff:** экспоненциальный с jitter. `delay = min(base * 2^(attempt-1), cap) ± random_jitter`. Ориентир: `base = 2000 мс`, `cap = 60000 мс`, jitter ±20%. `next_run_at = now + delay`.

### 3.9. Metrics / Telemetry

Считаются в рантайме, периодически пишутся в лог и доступны в финальном отчёте сессии. Источник истины — `parse_attempts` и счётчики статусов.

- Скорость парсинга — карточек/мин (скользящее окно).
- `cards_per_hour` — производная скорости.
- `success_rate`, `partial_rate`, `failed_rate` — доли от обработанных.
- `captcha_count` — число CAPTCHA-событий.
- `ban_count` — число `403/429`/`blocked`.
- `proxy_rotation_count` — число ротаций IP.
- `average_parse_time` — среднее `duration_ms` успешной карточки.

Метрики выводятся срезом за сессию и нарастающим итогом; используются для подтверждения критериев приёмки.

### 3.10. Rate Limiter

Защита от перегрузки целевого ресурса и собственной инфраструктуры. Параметры в конфиге.

- `max_cards_per_session` — потолок карточек за один запуск.
- `max_cards_per_minute` — троттлинг скорости (глобально).
- `max_session_duration` — максимальная длительность сессии воркера; по достижении — корректное завершение и пересоздание.
- `max_parallel_workers` — ограничение пула воркеров (увязано с RAM и числом прокси-каналов).
- **Лимит на один proxy channel:** `max_cards_per_proxy`, `max_requests_per_minute_per_proxy` — не давить один IP сверх порога; при достижении — ротация (п.4.2).

### 3.11. Raw Data Storage

Хранение сырого JSON/HTML в `raw_snapshots` (п.3.7). Назначение — отладка, восстановление при изменении парсинга, E2E-фикстуры.

- **Последние N карточек** (`purpose='recent'`) — кольцевой буфер, размер настраивается; для разбора свежих сбоев.
- **Карточки с ошибками** (`purpose='error'`) — сохраняются при `failed`/повторных ошибках.
- **CAPTCHA-события** (`purpose='captcha'`) — снимок страницы на момент детекта, связан с `captcha_events`.
- **Снимки для E2E** (`purpose='fixture'`) — отобранные эталоны для тестов из п.5.4.

Крупные payload допустимо хранить файлами на диске, в таблице — путь. Для сырых снимков предусмотреть TTL/очистку, чтобы не разрастаться.

### 3.12. Разделение модулей в рамках MVP

В MVP реализуется платформенное ядро и один источник — `2gis` через Source Adapter Layer. Сбор из 2GIS, обогащение, экспорт и хранение не смешиваются в один модуль.

- **2GIS Adapter** — источник-специфичная логика: поиск, список карточек, детали, раскрытие контактов, API Capture / DOM Fallback, маппинг raw → `Lead`.
- **Core Platform** — очередь, воркеры, состояние задач, retry, rate limit, storage, telemetry. Ядро не содержит логики 2GIS.
- **Normalizer** — общие правила качества данных после `adapter.normalize()`.
- **Lead Enrichment** — только архитектурный задел в MVP; полноценный обход сайтов компаний и Email Discovery оцениваются отдельно.
- **Exporter** — выгрузка `Lead` в XLSX/CSV.

Разделение модулей в платформенной версии раскрыто в п.8. Пункт 3.12 больше не является отдельной конкурирующей схемой, чтобы подрядчик не гадал на кофейной гуще, где тут правда.

### 3.13. Архитектурная схема

Актуальная архитектурная схема приведена в п.8.5. Старая схема v1.5 не используется как критерий реализации.

Поперечные подсистемы: Rate Limiter, Retry/Backoff Policy, Metrics/Telemetry, Raw Data Storage, Logging.

### 4.2. Алгоритмы обхода блокировок и стабильности

**Ротация IP**

После каждых **N карточек** или при HTTP `403` / `429`:

1. Пауза 15 секунд.
2. GET-запрос на API прокси для смены IP.
3. Ожидание успешного обновления сети.
4. **Пересоздание контекста браузера:** прокси задаётся при создании контекста Playwright, поэтому после смены IP старый контекст закрывается и поднимается новый. Это потеря 2–5 сек и сессионных кук — повторный вход в категорию обязателен, дедуп по `source + external_id` пропустит уже собранное. **Сброс кук считаем плюсом, а не багом:** обнуляются сессионные счётчики 2GIS, а значит и накопленные лимиты по IP/сессии.

`N` настраивается, стартовый диапазон **20–50**, **финальное значение калибруется на тестах** под конкретного прокси-провайдера.

**Рандомизация поведения**

Задержки между кликами рассчитываются динамически (`Math.random()`) в заданном диапазоне. Фиксированные тайминги запрещены.

**Обработка всплывающих окон**

Автоматическое закрытие: опросов, предложений установить приложение, гео-алертов и прочих перекрывающих интерфейс элементов.

### 4.3. Обогащение email (опциональный этап)

Если поле `email` критично для заказчика: после сбора карточки скрипт переходит на сайт компании (поле `website`) и ищет email на страницах контактов. Реализуется как отдельный модуль обогащения и оценивается отдельно.

### 4.4. Дедупликация

- Первичный ключ дедупа на уровне источника — пара `source + external_id`. Для MVP это `source=2gis` + `external_id=id_2gis`.
- **Дополнительно:** дедуп по нормализованному телефону, т.к. один бизнес может иметь несколько филиалов с разными внешними ID и общим номером. Правило слияния филиалов согласуется с заказчиком.

## 5. Нефункциональные требования

### 5.1. Отказоустойчивость (Error Handling)

**Парсинг с сохранением состояния**

Каждая спарсенная карточка сразу пишется в SQLite. После падения повторный запуск по той же категории продолжается с места остановки.

**Деградация без падения (graceful degradation)**

При недоступности отдельных полей (нет телефона, не раскрылся спойлер) карточка сохраняется частично и помечается флагом неполноты. Частичный сбор предпочтительнее остановки.

**Перезапуск контекста браузера**

При утечке памяти или зависании вкладки:

1. Корректно закрыть текущую сессию Playwright.
2. Поднять новый чистый инстанс.
3. Восстановить рабочий процесс с места остановки.

**Self-healing селекторов (новое)**

Недостаточно ловить факт поломки — нужна устойчивость к ней:

1. Для каждого поля хранится **массив селекторов-кандидатов**, пробуются по порядку.
2. **Regex/JSON-фоллбэк** по тексту страницы или перехваченному JSON, если ни один селектор не сработал.
3. Если все варианты не дали данных на **N карточек подряд** — поток останавливается и шлёт алерт «селекторы устарели», а не собирает пустые данные молча.
4. (Опционально) автотест селекторов на сохранённом HTML/JSON-снимке для раннего обнаружения.

### 5.2. Производительность

- Поддержка контролируемой многопоточности: несколько независимых контекстов браузера параллельно через разные прокси-каналы.
- Потребление RAM на поток: **ориентир до 800 МБ–1 ГБ** на инстанс Chromium с загруженным SPA 2GIS. Прежний лимит 400 МБ нереалистичен и заменён.
- Число параллельных потоков ограничивается доступной RAM и числом прокси-каналов.

### 5.3. Логирование

- Все действия — в консоль и в файл `app.log` через `winston`.
- **Ротация логов** через `winston-daily-rotate-file` (защита от разрастания файла при длительной работе).
- **Телеметрия:** счётчики `успех / частично / провал / бан` за сессию, выводятся в лог. Без них нечем подтвердить выполнение критериев приёмки.

Пример логов:

```text
[2026-06-01 20:10:15] [INFO] Инициализация сессии: Москва -> Автосервисы
[2026-06-01 20:11:02] [INFO] Успешно загружен список компаний. Найдено объектов: 342
[2026-06-01 20:11:15] [SUCCESS] Спарсена компания ID 7000000123: "Авто-Док", Тел: +79991112233
[2026-06-01 20:12:40] [WARNING] Обнаружена защита. Запрос смены IP прокси...
[2026-06-01 20:12:55] [INFO] IP прокси успешно изменен. Продолжение работы.
```

### 5.4. Тестирование

- **Юнит-тесты (обязательно):** нормализация телефонов к `+7XXXXXXXXXX`, логика дедупа (по `source + external_id` и по телефону, слияние филиалов).
- **E2E-тесты:** прогон Parser Core на **зафиксированных снимках HTML/JSON** реальных карточек 2GIS. Защищает от регрессий при обновлении stealth/селекторов.
- Снимки хранятся в репозитории как фикстуры; при поломке теста сразу видно, изменилась ли структура 2GIS.

## 8. Платформенная архитектура: Universal Lead Collection Platform (актуальная схема v1.7)

Раздел расширяет п.3 и переопределяет концепцию проекта. **Scrape2Lead перестаёт быть «парсером 2GIS»** и проектируется как **Universal Lead Collection Platform** — ядро для сбора и обогащения лидов из произвольных источников. В MVP реализуется только 2GIS Adapter.

Положения этого раздела и раздела 0 имеют приоритет над старыми формулировками п.3.12–3.13 и п.4.1. Стек неизменен: Node.js, TypeScript, Playwright.

### 8.1. Принцип

- **Ядро** (Job Manager, Queue, Worker Pool, Browser Session Manager, Storage, Normalizer, Enrichment, Exporter, Telemetry, Rate Limiter, Retry) не знает о конкретном источнике.
- **Источник** инкапсулирован в Source Adapter, реализующем единый контракт.
- Подключение нового источника = новый адаптер, **без изменений ядра**.

### 8.2. Source Adapter Layer

Новый слой между Worker Pool и Browser Session Manager. Воркер получает из очереди задачу с полем `source`, по нему резолвит нужный адаптер (реестр адаптеров) и работает через его интерфейс.

**Единый контракт адаптера (`ISourceAdapter`):**

| Метод | Назначение | Вход → Выход |
|---|---|---|
| `searchCompanies(query)` | Поиск компаний по гео/категории. | `{geo, category, filters}` → курсор/итератор списка. |
| `listCards(cursor)` | Постраничное/скролл-получение списка карточек. | `cursor` → `RawCardRef[]`, `nextCursor`. |
| `getCardDetail(ref)` | Детальная карточка. | `RawCardRef` → `RawCardDetail`. |
| `getContacts(ref, page)` | Раскрытие/добыча контактов (клики по спойлерам и т.п.). | → `RawContacts`. |
| `normalize(raw)` | Приведение сырых данных к модели `Lead` (п.8.4). | `RawCardDetail + RawContacts` → `Lead`. |
| `capabilities()` | Декларация возможностей (нужен ли браузер, поддержка API capture, требует ли прокси, есть ли CAPTCHA). | → `AdapterCapabilities`. |

**Запрет влияния источника на ядро.** Адаптер НЕ обращается напрямую и НЕ меняет: Queue Layer, Job Manager, Worker Pool, Browser Session Manager, Storage Layer, Enrichment Worker, Exporter, Telemetry. Он только реализует контракт; ресурсы (страницу браузера, прокси) получает через переданный контекст исполнения, а не управляет ими сам.

**Точки интеграции:**
- Вверх: Worker Pool вызывает методы контракта.
- Вбок: Browser Session Manager предоставляет `Page` (если `capabilities().needsBrowser`).
- Вниз: результат `normalize()` идёт в Storage Layer через Normalizer.
- Сквозные: Telemetry/Retry/Rate Limiter работают по статусам и ошибкам, одинаково для всех адаптеров.

### 8.3. Реестр адаптеров

```text
Source Adapter Layer
├── 2GIS Adapter          (реализован, тестовый полигон)
├── Google Maps Adapter   (план)
├── Yandex Maps Adapter   (план)
├── Avito Adapter         (план)
├── HH Adapter            (план)
├── Custom Website Adapter(план)
└── Future Adapters
```

Для каждого адаптера определяется:

- **2GIS Adapter** — карты/справочник. Браузер: да. API capture: да (XHR/GraphQL) + DOM fallback. Прокси: резидентные/мобильные. CAPTCHA: да. Данные: полный профиль карточки + контакты под спойлером.
- **Google Maps Adapter** — карты. Браузер: да. Особенность: агрессивный антибот, ограниченные контакты; возможен официальный Places API как альтернатива (вне браузера). Прокси: да.
- **Yandex Maps Adapter** — карты/справочник РФ. Браузер: да. CAPTCHA SmartCaptcha вероятна. Прокси РФ.
- **Avito Adapter** — объявления. Браузер: да. Жёсткий антибот, телефоны под кликом/за токеном. Прокси мобильные.
- **HH Adapter** — вакансии/компании. Возможен официальный API → адаптер без браузера (`needsBrowser=false`). Данные: компании-работодатели.
- **Custom Website Adapter** — произвольный сайт по конфигу (селекторы/правила). Браузер: опционально. Используется для обхода сайтов компаний (пересекается с Enrichment).
- **Future Adapters** — любой источник, реализующий `ISourceAdapter`.

Каждый адаптер декларирует: ответственность (какой источник, какие данные), точки интеграции (нужен ли браузер/прокси/CAPTCHA-стратегия), интерфейсы (реализация контракта), требования к данным (какие поля модели `Lead` он способен заполнить, какие — никогда).

### 8.4. Унифицированная модель `Lead`

Все адаптеры приводят данные к единой сущности. Заменяет источник-специфичную структуру п.4.1 на уровне ядра (поля 2GIS становятся частным случаем).

| Поле | Тип | Описание |
|---|---|---|
| `source` | String | Идентификатор источника (`2gis`, `google_maps`, ...). |
| `external_id` | String | ID записи в источнике (бывший `id_2gis`). Уникален в паре с `source`. |
| `company_name` | String | Наименование. |
| `category` | String | Рубрика. |
| `city` | String | Город. |
| `address` | String | Адрес. |
| `phones` | Array | Телефоны, нормализованные к `+7XXXXXXXXXX` (правила нормализации зависят от региона источника). |
| `email` | String / Nullable | Email. |
| `website` | String / Nullable | Сайт. |
| `social_links` | Array | Соцсети (обобщение `social_vk` и прочих). |
| `messenger_links` | Array | WhatsApp/Telegram/Viber и др. |
| `parsed_at` | DateTime | Метка сбора. |

**Дедуп-ключ:** `UNIQUE(source, external_id)` + сквозной дедуп по нормализованному телефону между источниками (мульти-сорс агрегация, п.8.8).

**Процесс нормализации:**
1. Адаптер возвращает сырые данные (`RawCardDetail`, `RawContacts`).
2. `adapter.normalize()` маппит источник-специфичные поля на `Lead`.
3. Общий **Normalizer ядра** применяет источник-независимые правила: формат телефона, тримминг, валидация email/URL, дедуп, флаг неполноты.
4. Результат пишется в Storage Layer.

Разделение: адаптер знает структуру источника, Normalizer знает правила общей модели. Источник-специфичная логика не протекает в ядро.

### 8.5. Актуальная архитектурная схема MVP

```text
CLI / Local API
        ↓
   Job Manager
        ↓
 Queue / Scheduler
        ↓
   Worker Pool
        ↓
Source Adapter Layer        ← резолв адаптера по job.source
        ↓
2GIS Adapter                ← единственный адаптер в MVP
        ↓
Browser Session Manager     ← если adapter.capabilities().needsBrowser
        ↓
API Capture / DOM Fallback  ← внутри адаптера / Parser Core
        ↓
   Normalizer
        ↓
  Storage Layer
        ↓
 XLSX / CSV Exporter
```

Сквозные подсистемы: Rate Limiter, Retry/Backoff, Telemetry, Raw Data Storage, Logging.

**Не входят в схему MVP:** Lead Scoring, CRM Integration, Analytics Dashboard, дополнительные адаптеры. Они описаны в п.8.8 как будущие возможности и не используются как критерии первой поставки.

### 8.6. Масштабируемость: подключение нового источника

Подключение будущего источника НЕ требует правок ядра. Для MVP этот процесс проверяется на одном источнике — `2gis`. Для каждого следующего источника нужно:

**Создать файлы:**
- `src/adapters/<source>/<Source>Adapter.ts` — реализация `ISourceAdapter`.
- `src/adapters/<source>/selectors.ts` или `apiRoutes.ts` — источник-специфичные селекторы/эндпоинты.
- `src/adapters/<source>/mapper.ts` — маппинг raw → `Lead`.
- `src/adapters/<source>/index.ts` — регистрация в реестре адаптеров.

**Реализовать интерфейсы:** `ISourceAdapter` (все методы п.8.2) + `capabilities()`.

**Добавить тесты:**
- Юнит: `mapper` (raw → `Lead`), нормализация телефонов под регион источника.
- E2E: прогон адаптера на зафиксированных снимках источника (фикстуры `raw_snapshots`, п.3.11).
- Контрактный тест: адаптер удовлетворяет `ISourceAdapter` (общий тест-набор, прогоняется для каждого адаптера).

Регистрация в реестре — единственная «точка касания» с системой; ядро, очередь, хранилище и экспортер не меняются.

### 8.7. Роль 2GIS в проекте

- 2GIS — **первый адаптер** и тестовый полигон, не цель проекта.
- На нём проверяется антибот-архитектура (stealth, fingerprint-патчи, детект-тесты — п.2.1).
- На нём тестируются: очереди и Job Manager, ротация прокси, обработка CAPTCHA, хранение состояния и сырых данных, отказоустойчивость и восстановление.
- **Успешная работа с 2GIS считается доказательством работоспособности платформы** (самый сложный из планируемых источников по антиботу).
- Архитектура НЕ должна зависеть от 2GIS: удаление 2GIS-адаптера не должно ломать ядро; критерии приёмки v1.0–v1.5 проверяются через 2GIS-адаптер, но формулируются в терминах платформы.

### 8.8. Будущие возможности платформы

Архитектурно предусмотрены (реализация — отдельные этапы вне текущего объёма):

- **Lead Enrichment** — дополнение лида (уже выделен отдельным воркером, п.3.12).
- **Email Discovery / Company Website Crawling** — поиск email обходом сайтов (через Custom Website Adapter + Enrichment Worker).
- **Lead Scoring** — оценка качества лида; отдельный слой после Enrichment (см. схему 8.5).
- **CRM Integration / CRM Export Layer** — выгрузка/синхронизация с внешними CRM поверх Exporter.
- **Analytics Dashboard** — визуализация метрик Telemetry.
- **Multi-source Aggregation** — слияние лидов из нескольких источников по дедуп-ключу `phone`/`website`; `Lead` уже несёт `source`/`external_id` для этого.

Эти возможности не входят в текущий объём работ и реализуются как отдельные адаптеры/слои без изменения ядра.

## 10. Критерии успешной приемки MVP

Проект считается принятым, если выполнен объём первой поставки из раздела 0: платформенное ядро + Source Adapter Layer + рабочий 2GIS Adapter. Дополнительные адаптеры, Lead Scoring, CRM Integration и Dashboard не входят в критерии MVP.

1. Система запускает задачу `source=2gis`, `geo`, `category` через Job Manager и Queue / Scheduler.
2. 2GIS Adapter реализует контракт `ISourceAdapter`: `searchCompanies`, `listCards`, `getCardDetail`, `getContacts`, `normalize`, `capabilities`.
3. Парсер обрабатывает категорию 2GIS без ручного вмешательства по одному из согласованных уровней:
   - **Бытовой:** 500 компаний, доля успешных лидов ≥ 50%.
   - **Боевой:** 1000 компаний, доля успешных лидов ≥ 85%.
   - Планка 90% реалистична только с решателем CAPTCHA; без него не использовать как критерий приёмки.
4. Сбор телефонов корректно раскрывает спойлеры интерфейса 2GIS.
5. CAPTCHA детектируется и обрабатывается без падения всей системы.
6. Данные сохраняются в единой модели `Lead` с ключом `source + external_id`; для 2GIS: `source=2gis`, `external_id=id_2gis`.
7. Итоговый XLSX/CSV открывается без ошибок и содержит нормализованные поля `Lead`.
8. Телефоны стандартизированы до `+7XXXXXXXXXX` для РФ/КЗ.
9. Дубликаты отсутствуют по `source + external_id` и по нормализованному телефону с учётом согласованных правил слияния филиалов.
10. При устаревании селекторов система шлёт алерт/логирует критическое событие, а не собирает пустые данные молча.
11. Retry / Backoff, Rate Limiter, Proxy Rotation и Browser Restart работают по правилам ТЗ и фиксируются в `parse_attempts`, `proxy_history`, `captcha_events`.
12. Raw Data Storage сохраняет снимки ошибок, CAPTCHA и E2E-фикстуры.
13. Код написан на TypeScript, структурирован по модулям и не содержит источник-специфичной логики 2GIS внутри ядра.
14. Юнит-тесты на нормализацию и дедуп проходят.
15. Контрактный тест `ISourceAdapter` для 2GIS Adapter проходит.
16. E2E-тесты на зафиксированных HTML/JSON-снимках 2GIS проходят.
17. Переданы: репозиторий, `.env.example`, инструкция запуска, миграции, команды тестов, пример экспорта.
