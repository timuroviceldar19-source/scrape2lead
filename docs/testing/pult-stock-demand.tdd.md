(«склад: 69 шт · 75″»), и подаётся с товаром из наличия. Директор на «Финансах» у позиции без расхода видит спрос
(«спрос: 3 лота на 24 шт») и ведёт склад в конкретные лоты. Все данные в тестах выдуманные

## Решения

1. **Сопоставление считает сервер.** `page/*.client.js` — только рендер, поэтому диагональ и подбор строк склада
   живут в `stock/availability.ts`, а страница получает `payload.stock.hints`: одинаковый результат
   `{ qty, diagonal, approx }` — один элемент со списком ID сделок (лоты Радара всех колонок и открытые планы).
   Парсер диагонали один, клиент его не дублирует. `window.__stockHint(item)` ищет подсказку по `item.id` и выбирает
   класс: `good` — хватает на `item.qty`, `warn` — меньше, `approx` — итог по виду (нейтральный цвет). ID без склада в
   подсказки не попадают — тега нет.
2. **Диагональ** — только у «Интерактивных панелей» и «Мониторов», только из списка 55/65/75/85/86/98/100/110:
   число с маркером (″, ", ”, '', «дюйм», «-дюймовая», «-ти дюймовая»), а у панели ещё и отдельное число в названии со словом
   «панель». Не диагональ: число внутри модели («IFP7502»), с единицами после («100 шт», «75 см», «3840x2160»), после «№».
   Две разные диагонали («65/75») — `null`. Мониторы 22–27″ в список не входят и сопоставляются по виду (`approx`),
   «Монитор Пример 75» без маркера — тоже без диагонали: число у монитора чаще модель.
3. **Принадлежности не склад товара.** `classifyProductGroup` относит «Кронштейн для интерактивной панели» к панелям.
   Функции Радара не менялись: перед ними `classifyStockName` отсевает названия, которые начинаются с принадлежности
   (кронштейн, крепление, стойка, пульт, кабель, картридж, сумка…), и названия, где «для» стоит раньше слова товара
   («Стойка мобильная для панелей»). «Ноутбук для учителя» остаётся ноутбуком.
4. **`matchStock`.** Диагональ в названии карточки — строки этой диагонали (`approx: false`). Такой диагонали на складе
   нет — панели неизвестного размера, если есть (`approx: true`, `diagonal: null`), иначе `null`: 65″ из 75″ не
   подсказываем. Диагонали в названии нет или вид без диагоналей — итог по виду, `approx: true` (модель не сверена).
5. **Спрос** (`buildStockDemand`) — лоты Радара «Подать сегодня» и «Успеть с замечанием» и открытые планы; «Второй шанс»
   не входит. Лот входит в каждую строку склада, которую ему подобрал бы `matchStock`. План с тем же номером плана, что у
   лота Радара (номер плана у лота — цифры до дефиса, как в дедупликации «Второго шанса»), считается один раз. Для панелей
   и мониторов `approxLots` — сколько лотов подошли без точной диагонали; на «Финансах» это «· из них 1 без диагонали в
   названии», чтобы спрос по названиям без размера не выглядел точным. Вид без диагоналей — `approxLots: 0`.
6. **Позиция → ключ на «Финансах»** считается на сервере: `buildFinanceInsights` кладёт `stockKey` каждой позиции без
   расхода (`stockKeyOfName` из `stock/classify.ts`), в `FinancePagePayload.stockDemand` — строки спроса
   `{ key, lots, qty, approxLots }`. `fin.client.js` только соединяет их по ключу. Готовые строки «для топ-5» не выбраны:
   тогда страница зависела бы от порядка двух массивов. Строка спроса добавлена и в текст «Скопировать для ОП».
   `classify.ts` отделён от `availability.ts`, чтобы не было цикла импортов `insights ↔ availability`.
7. **Устаревший отчёт** — старше 3 дней на дату сборки (`STOCK_STALE_DAYS`): у тега пометка «на dd.mm».
8. **Тег.** Видимый текст по заданию («склад: 69 шт · 75″», «склад: 83 шт · ≈ по виду»); цвет не единственный носитель
   смысла — для экранного диктора скрытый `.stock-sr` («, хватает на закупку» / «, меньше, чем в закупке (20 шт)» /
   «, приблизительно: …»), в `title` — дата отчёта и «только штуки, без цен». Тег не интерактивный, в порядок Tab не
   попадает. На ТВ скрыт (`body.tv .stock-tag`). В строке плана тег стоит в ячейке «Товар / вид»: колонка количества
   (75 px) на 1440 ломала тег на четыре строки.
9. **Роли.** `payload.stock` идёт в вид менеджера сам (`filterPultPayload` переносит остальные поля), `variants/manager.ts`
   не менялся. `scripts/pult-variants.mts` при чтении `payload.json` проверяет склад zod-схемой со `.strict()`: неверный
   формат или лишнее поле (сумма, компания) — поле выкидывается, в лог только число ошибок, выкладка продолжается. Затем
   `stockForViewer` оставляет в подсказках только ID карточек и планов, которые есть в виде: сейчас у менеджера нет Радара,
   остаются его открытые планы. Если Радар откроют менеджеру, фильтр подхватит его карточки сам. Строки склада
   (`rows`, со `stagnantQty`) остаются — это штуки, без цен.
10. **Штуки.** Берётся `endQty > 0`; единицы измерения не фильтруются (у ИП/КТ это шт/компл), сумма округляется до 0,001.
11. **Лог сборки** (`[Склад] строк по видам: N, карточек с подсказкой: M, строк спроса: K`) — только счётчики.

## Для интеграции

Общие файлы тронуты точечно: `types.ts` (поле `stock` перед `plans`), `site.ts` (`stockClientJs` перед plans/radar,
поле `FinancePagePayload.stockDemand`), `page/radar.client.js` (одна строка после `priceHtml` в `renderCard`),
`page/plans.client.js` (хук в ячейке «Товар / вид»), `page/pult.css` (блок `.stock-tag` после `.win-price`),
`scripts/sales-pult.mts` (режим site: блок после литерала `payload`, `stockDemand` в `finPayload`),
`scripts/pult-variants.mts`, `finance/insights.ts` (`stockKey`), `page/fin.client.js`, `page/fin.css`.

## Интеграция с Радаром менеджера и пульсом (ветка `feat/pult-decision`)

- RED: `tests/bitrix/salesPultPulseSources.test.ts` — `stockDemandPulseItems` нет; `buildManagerVariant` оставлял
  в `stock.hints` ID чужих сделок (обрезка была только в `scripts/pult-variants.mts`).
- GREEN: обрезка `stockForViewer` перенесена в `buildManagerVariant` (семантический слой): вид менеджера безопасен
  при любой сборке; в `pult-variants.mts` осталась только zod-проверка `payload.stock`.
- После слияния с агентом «Радар» у менеджера есть свой Радар, поэтому в его странице теперь есть свои лоты
  (5101 в фикстуре) и подсказки склада к ним; чужие лоты и планы по-прежнему не попадают
  (`salesPultStockBrowser.test.ts` обновлён).
- Пульс: пункт «Склад без расхода нужен в лотах» (`stock-demand`, жёлтый, закрытый, ссылка на склад «Финансов»):
  только виды, где есть и товар без расхода (`stagnantQty`), и спрос открытых лотов и планов; штуки, без денег,
  поэтому от порога суммы неподвижного склада не зависит. Утром спрос считается только по лотам радара.
