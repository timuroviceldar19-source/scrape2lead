# Итоги сделок: открытый API zakup

## Правки перед слиянием, 30.10.2026

- Новый ключ `published`/`failed`/`cancelled`/`contract-draft`/`repurposed` разрешён только при совпадении самой новой версии портала с версией источника и при том же ключе, вычисленном из строки портала. Исходы договоров не требуют этой проверки.
- `src/kz/goszakupPlanRegistry.ts` — общее чтение реестра, точный отбор номера, защита от коротких страниц, пауза, кэш и общий deadline HTML. `source_conflict`, `portal_unavailable`, `html_budget` сохраняются в частном JSON и счётчиках; запись по ним запрещена, прогон продолжается.
- Полные обходы заказчик/годы ограничены `--max-full-scans` (по умолчанию 2). Кэш не расходует слот повторно; предел действует и при чтении договоров, резерв ows его не обходит. Пропуски учитываются отдельно.
- RED: новый модуль отсутствовал, тест потолка получил успешный пустой результат вместо отказа. Команды: `npm test -- tests/kz/goszakupPlanRegistry.test.ts tests/kz/zakupGzPlans.test.ts`, `npm test -- tests/bitrix/gzOutcomePortal.test.ts`.
- GREEN: `npm test -- tests/kz/goszakupPlanRegistry.test.ts tests/kz/zakupGzPlans.test.ts tests/kz/zakupGzRegistry.test.ts tests/bitrix/gzOutcomePortal.test.ts` (см. локальный `tmp/zakup-review-20261030/outcomes-green.txt`); `npm run lint` успешен (`outcomes-lint.txt`).
- Покрытие новой проверки: 97,27% строк, 80,26% ветвей (`portal-coverage.txt`, `npm run test:coverage -- tests/kz/goszakupPlanRegistry.test.ts tests/bitrix/gzOutcomePortal.test.ts --coverage.include=src/kz/goszakupPlanRegistry.ts --coverage.include=src/bitrix/gzOutcomePortal.ts`).
- Повторный живой dry-run запускается с пустым токеном ows и обёрткой, запрещающей любые методы записи. Результаты будут отражены после завершения команд; предварительные цифры не выдаются за итоговые.

Задача: итоги и статусы без обязательного GOSZAKUP_TOKEN. Секреты и данные CRM в репозиторий не включаются.

## Решения

- Сначала zakup, при ошибке и заданном токене — ows. Успешный пустой ответ не включает резерв. При двух ошибках сохраняются обе причины.
- Год переводится через `/dicts/years/`, БИН — через общий `data/market/orgs.json`, обратный поиск по значениям.
- Позиции договора проходят `dedupeSubjects`; `plan_item.external_id` — версия, `root.external_id` — номер пункта. Сумма берётся без НДС.
- Поиск корня: `plan-items/?q=...`, обязательное совпадение БИН и год не раньше сделки. Если результата нет — договоры заказчика с полным `enstru_code`, `sign_date__gte` и годом из справочника; затем позиции и точная связь `root.external_id`. Проверяются прежний и текущий коды товара. Префикс кода не используется.
- Дополнительный путь: `lots/?plan_item_external_id=<версия>` → объявление → `announcements/{id}/contracts/`. Последний ответ содержит позиции; договор дочитывается по проверенному номеру. Полный обход заказчика допускается только без полного кода ЕНС ТРУ.
- Если индекс кода не вернул ранее записанный договор, его номер служит ключом узкого повторного поиска. Сам прежний исход не используется как доказательство: позиции, поставщик и прежние правила сопоставления проверяются заново. Пустой набор номеров не вызывает полный обход.
- Чтение позиций отделено от обогащения поставщика: для поиска версии пункта БИН поставщика не нужен. В памяти кэшируются карточки, позиции и область поиска; результаты полного обхода при повторном использовании ограничиваются кодами и проверенными пунктами.
- HTML остаётся в существующем резерве скрипта. Новый основной HTML-поиск отменён после уточнения задачи.
- Названия статусов берутся из справочников/карточек ЭГЗ с непустым `egz_code`. Правила решений не меняются.
- `is_externally_deleted`, если присутствует, переводится в `deleted`. Публичная карточка договора в исследованном ответе этого поля не содержит; полную эквивалентность старому флагу удаления подтвердить нельзя. Статус расторжения удалением не считается.
- `timestamp` не используется как доказанная дата создания версии. Для проверки возраста товара берётся консервативная дата акта; без неё правка товара запрещена.

## Измеренные результаты

Предварительная выборка: 100 пунктов со старым статусом; q нашёл 38, все прошли БИН и год, статус совпал у 20, отличался у 18. Запросов 139, время 7,470 с (`q-sample-summary.json`). Старый исследовательский полный обход добавил 26 пунктов, оставил 36 и занял 911,133 с (`q-contracts-summary.json`). Он заменён узкими фильтрами, это не время итоговой реализации.

Финальный dry-run: 1029 сделок; исходы с договором найдены через код для 291 сделки, через сохранённый номер ещё для 50; через объявление, полный обход и ows — по 0. План по корню найден через q у 361 сделки, через позиции отфильтрованных договоров у 194; прочие пути — 0. На входе 51 сделка без полного кода; после существующего чтения пунктов, включая HTML-резерв, таких 0. Полных обходов заказчика 0. Это счётчики разных этапов, их нельзя складывать как уникальные сделки (`outcomes-verified.txt`, `lookup_stats`).

Повторно проверено 54 сделки по 42 сохранённым номерам. Из прежних проигрышей 309 из 315 воспроизвелись, 4 остались без сигнала, 2 пропущены из-за недоступных позиций другого договора заказчика. Из 4 без сигнала у 3 отсутствует проверяемая связь корня/версии в публичных позициях, 1 договор не находится по номеру (`outcome-final-comparison.txt`, `registry-gaps.txt`; команды агрегирования — в частном отчёте). Отсутствие сигнала не удаляет сохранённый маркер. Выигрыши и расторжения воспроизвелись полностью в проверенной выборке; подробное сравнение по всем видам хранится вне Git.

Итоги: 7090 сетевых запросов (6646 zakup, 420 портал, 24 CRM), 1476,008 с. HTTP-кэш отключён, штатный кэш организаций сохранён. Было 9 неудачных HTML-проверок и 1 заказчик с недоступными позициями; это не безошибочный прогон, несмотря на код выхода 0 (`outcomes-verified.txt`, `outcomes-verified-metrics.json`). Последовательность «итоги → товар» заняла 1701,603 с и завершила обе команды с кодом 0 (`morning-verified-job.txt`), укладываясь в лимит job 40 минут; прежнее фактическое время ows не измерено.

Полный набор: 1503 теста пройдены, 9 пропущены (`npm test > .../final-tests.txt`); `npm run lint` и `npm run build` успешны (`final-lint.txt`, `final-build.txt`, коды в `final-checks.json`). Покрытие пяти адаптеров: 98,07% строк, 85,34% ветвей (`final-coverage.txt`, команда в частном отчёте). `npm audit --json > .../final-audit.json` показывает 18 существующих проблем зависимостей; зависимости этим изменением не менялись.

## Ограничение готовности

Совместимость перевода статусов не доказывает актуальность индекса zakup. В сверке обнаружены расхождения текущих версий/статусов с официальным порталом, включая отсутствующую в zakup более новую версию. Пока они не разрешены, перенос готов к просмотру, но не к массовой записи. Время изменения относительно 29.10 и эквивалентность флага удаления договоров не доказаны. Частные отчёты и примеры CRM не включены в репозиторий.
