# Чат-бот-помощник в Bitrix24: журнал TDD

Цель: менеджер пишет боту в чат Bitrix24 («оцени сделку 41293», «кто контакт у заказчика») и получает ответ.
Бот только читает: в сделки и контакты Bitrix он ничего не пишет.

## Решения

- **Бот через входящий вебхук с правом `imbot`**, Chatbots 2.0 (`imbot.v2.Bot.register`, ответ — `imbot.v2.Chat.Message.send`).
  Режим доставки `fetch`: программа сама опрашивает `imbot.v2.Event.get`, публичный адрес не нужен.
- **Запуск на маленьком сервере (Node, Docker-образ), не на Cloudflare Workers.** Проверка в локальном движке Workers
  (workerd): `ows.goszakup.gov.kz` отвечает, а `procurement.gov.kz` падает с `internal error` — у портала неполная цепочка
  сертификата (см. AGENTS.md, «TLS портала»). В Node это решает `NODE_EXTRA_CA_CERTS`.
  Повторено на реальных серверах Cloudflare (13.10.2026, временный Worker в панели Cloudflare, затем удалён):
  `procurement.gov.kz` → **526** (Invalid SSL certificate), `goszakup.gov.kz` → 301, `ows.goszakup.gov.kz` → 302,
  `example.com` → 200. Страницы закупок и PDF с Cloudflare недоступны; доступен только API-хост.
- **GitHub Actions для бота не используем:** он не предназначен для постоянно работающих сервисов.
- **Контакты заказчика.** Страница закупки (`/ru/announce/index/<id>`) в блоке «Информация об организаторе» отдаёт
  `ФИО представителя`, `Должность`, `E-Mail`. Телефона заказчика там нет (встречаются только телефоны поддержки портала).
  Это персональные данные: храним и показываем только рабочие контакты, в логи не пишем.
- Файлы и страницы портала публичные и открываются без токена; `GOSZAKUP_TOKEN` нужен только для API
  (прошлые закупки заказчика по БИН).

## Вебхуки Bitrix

У входящего вебхука нет режима «только чтение»: права задаются по модулям (`imbot`, `crm`), а действует вебхук от имени
создавшего пользователя. Поэтому разделяем по модулям: один вебхук только с `imbot` (бот), второй только с `crm`
(чтение сделок). «Только чтение» обеспечиваем кодом: бот вызывает у CRM лишь методы `get`/`list` из белого списка.

## Срез 8: исправления после живой проверки срезов 7

Менеджер прислал ответ бота («оцени последние пару сделок»): бот утверждал, что пункт плана 83132229 — это НИОКР, а пункт 83718506 не найден, и не мог найти БИН
заказчика. Проверка по реестру показала две ошибки в самом боте (не в данных):

1. **Номер лота не равен номеру пункта плана.** Лот `83132229-ЗЦП1` в реестре ссылается на пункт `88224537` (`Lots.pointList`), а число перед дефисом — номер
   старого пункта, который потом изменили: `Plans(id: 83132229)` — это другая позиция («Работы по исследованиям…», статус «Изменён»), а `83718506` вообще не найден.
   Раньше `plan_status` принимал номер лота и брал число перед дефисом, поэтому оценка уходила не туда.
   Теперь `plan_status` принимает только номер пункта плана (лот отклоняет с подсказкой), а новый `lot_info` ищет лот по `lotNumber` и отдаёт `pointList`, БИН и название
   заказчика (`customerBin`, `customerNameRu`), статус, настоящий срок и ТЗ. Для сделок по лотам это же закрыло «БИН не найден»: у них нет БИН в сделке и компании CRM.
2. **Срок в Bitrix (`CLOSEDATE`) не срок приёма заявок.** У лотовых сделок `BEGINDATE` = день создания, `CLOSEDATE` = +7 дней (значения по умолчанию Bitrix), тогда как в реестре
   приём заявок идёт 2 дня и во многих сделках давно закончился (в выборке из 12 сделок «до 13.10» закупки были отменены, состоялись или не состоялись ещё 7–8.10).
   Список «что горит» из среза 7 показывал эти даты и мог ввести менеджера в заблуждение (например, у сделки 48667 в Bitrix 20.10, в реестре 15.10 15:35).
   Теперь `my_deals` не читает `CLOSEDATE`: он берёт последние 60 открытых лотовых сделок менеджера, запрашивает каждый лот в реестре (`lotsInfo`, до 6 запросов
   параллельно), оставляет закупки со статусом «Опубликован…» и сроком позже «сейчас по Алматы», сортирует по сроку и честно пишет, сколько лотов проверено и сколько не удалось.

RED: 3 теста `GoszakupApi.lotInfo/lotsInfo`, 3 теста `CrmReader.listMyDeals` (без CLOSEDATE, `scope`/`order`, страницы по 50), 9 тестов инструментов (`lot_info`, отказ `plan_status` на номер лота,
`my_deals` по реестру, часы Алматы). GREEN: 144 теста в `tests/assistant`, `npm run lint` чистый.
Живая проверка: тот же вопрос теперь оценивает лот 83718506 по реальному пункту плана 88054034 (цена в плане совпала со сделкой, медиана рынка 436 тыс., срок 15.10 16:36);
«что горит» показывает 31 живую закупку из 60 проверенных, самая срочная — сегодня в 23:05 (Алматы).

## Срез 9: «найди поставщиков Жасыл даму» (14.10.2026)

Начальник попросил найти поставщиков заказчика, из которых можно сделать агентов. Бот ответил, что БИН не нашёл, и показал только 15 последних договоров.
Разбор показал три причины.

1. **БИН из компании сделки почти никогда не читался.** Робот пишет `ORIGIN_ID` компании как `gz-company:<БИН>` (выборка из 300 последних компаний: 289 с приставкой, 11 пустых),
   а код принимал только «голые» 12 цифр. Ранее проверенная сделка случайно попала на старую карточку с «голым» БИНом.
   Исправлено: `binFromOriginId` принимает оба вида.
2. **Реестр ищет организацию только по точному названию** (`Subjects(filter:{nameRu})`: «Жасыл даму» → 0, «Жасыл» → одна пустая запись).

- Инструмент `customer_in_crm` (БИН или номер компании).
