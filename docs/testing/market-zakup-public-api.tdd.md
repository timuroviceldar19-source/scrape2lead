## Зачем

- В справочниках `/dicts/contract-statuses/` и `/dicts/purchase-methods/` у записей есть `egz_code` — код старого портала. Через него работают прежние `excludedStatuses` и названия способов из `config/market-monitor.json`.
- С IP GitHub (прогон 40917884404, 17:05 UTC): zakup ответил на 25 запросов из 25, ows в тех же заходах — на 2 из 5.

## Добавление 01.11.2026: жидкокристаллические панели в рынке ИП

Сбор планов ищет панели по трём названиям, в том числе «Панель жидкокристаллическая» (коды 279020.100.*), а рынок ИП на пульте их не считал. По просьбе пользователя они добавлены в группу ИП отдельным видом «Жидкокристаллические панели».

Проверка на живых данных: в открытом реестре zakup за октябрь 2026 под 279020.100.* 43 договора, и у всех позиций в этих кодах название «Панель жидкокристаллическая». Поэтому берётся весь префикс `279020.100.`, а не отдельные коды. Со всеми видами рынок ИП за октябрь — 403,9 млн ₸, из них жидкокристаллические панели — 134,1 млн ₸ (37 договоров).

RED: тест `counts LCD panels (279020.100.*) in the IP market and fetches them by prefix` в `tests/kz/marketFilter.test.ts` падал (`expected null to deeply equal { group: 'ИП', … }`).

GREEN: в `config/market-monitor.json` у группы ИП добавлены префикс `279020.100.` и вид с шаблоном `^279020\.100\.`, подпись кодов на вкладке рынка дополнена.

Кэш рынка утренний прогон обновляет только за последние 45 дней. Чтобы панели появились и в более ранних месяцах графика, нужна докачка: запуск `sales-pult.yml` с `market_backfill_from=2026-01-01`.

## Исправление 01.11.2026: докачка после смены кодов рынка

Докачка рынка (`--market-backfill-from`) пропускала месяцы, отмеченные в кэше как полные. После добавления ЖК-панелей январь–октябрь остались бы без них: месяцы уже «полные», а скачаны по старому списку кодов.

Теперь кэш помнит отпечаток правил отбора (`marketConfigKey`: группы и коды, фильтры, способы закупки, наши БИН). Если отпечаток другой или его нет (кэш до этой правки), докачка скачивает все месяцы заново и записывает новый отпечаток. Утреннее обновление за 45 дней отпечаток не меняет: старые месяцы оно не перекачивает.

RED (`tests/kz/marketBackfill.test.ts`): `marketConfigKey is not a function`; докачка кэша без отпечатка запрашивала только февраль (`expected [ '2026-02' ] to deeply equal [ '2026-01', '2026-02' ]`).

GREEN: 4 теста — полные месяцы при том же отпечатке пропускаются, при другом скачиваются заново, утреннее обновление сохраняет старый отпечаток, новые коды группы меняют отпечаток.

## Исправление 01.11.2026: ows обрывает список договоров

Полная докачка через zakup не помещается в Actions: договоров с кодом только в позициях за январь–октябрь 284 тыс., на каждый нужен отдельный запрос (≈6,5 ч при лимите job 6 ч), а фильтра по коду позиции у zakup нет. Поэтому рынок 2026 года пересобирается через ows (договоры по дате подписания, коды позиций приходят сразу).

Первая пересборка через ows отдала февраль только за 13–28 число: 542 позиции вместо 1305 в прежнем кэше. Проба тем же фильтром (`signDate` 01.02–28.02, страницы по 200, курсор `after` = наименьший id страницы) прошла 1197 страниц и получила все 239 395 договоров, которые ows насчитывает в `totalCount`. По ходу пробы ows несколько раз подвисал на минуты. Значит, в первой пересборке одна из страниц под нагрузкой пришла с `hasNextPage: false` посреди списка, а `fetchMarketContracts` принял это за конец, и неполный месяц записался в кэш как полный.

Теперь `fetchMarketContracts` сверяет число полученных договоров с `totalCount`. Если ows закончил список раньше, ту же страницу запрашивают ещё раз (до `maxRetries` раз с растущей паузой), а оборванный ответ не учитывается, чтобы договоры не задвоились. Если список так и не дошёл до `totalCount`, выбрасывается ошибка «получено N из M договоров», и докачка не отмечает месяц полным. Страница с `hasNextPage: true` без курсора тоже ошибка: раньше на ней сбор молча останавливался.

RED (`tests/kz/marketOwsFetch.test.ts`): все 4 первых теста падали — `fetchMarketContracts` не принимал подменный `fetchFn` и ходил в настоящий ows (403 на фиктивный токен), а сверки с `totalCount` не было. Тест на задвоение добавлен после первой версии исправления: она учитывала оборванную страницу и при повторе считала её договоры дважды.

GREEN: 5 тестов — повтор страницы после обрыва, без задвоения частично оборванной страницы, ошибка при стойком обрыве, ошибка без курсора, список ровно до `totalCount` без лишних запросов.
