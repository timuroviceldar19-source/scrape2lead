# GZ: планы с zakup.gov.kz вместо замёрзшего реестра портала — журнал TDD

## Откуда задача

18.11.2026 на вопрос «что по планам» выяснилось: с 13.11.2026 робот не завёл ни одного нового плана. До этого
было 4–17 планов панелей и 9–28 планов ПК в будний день. Робот исправен: сбор каждый раз находил одни и те же
~64 плана панелей и ~258 планов ПК, самая новая «Дата акта» в выгрузках — 12–13.11.

Причина: публичный реестр планов `procurement.gov.kz/ru/registry/plan` перестал пополняться. Самый новый пункт
во всём реестре за 2026 год — 88654473. Открытый API `zakup.gov.kz` отдаёт пункты тех же номеров дальше
(88744121 на 18.11), а лоты на портале при этом ищутся нормально. Пользователь: «Да, переведи».

## Что отличает zakup от портала

Проверено на живых данных 18.11 (только чтение):

- Номера пунктов (`external_id`) совпадают с номерами портала, поэтому `ORIGIN_ID gz-plan:<номер>` у старых
  сделок совпадает.
- Год задаётся справочником `/dicts/years/` (12 = 2026; 2027 там пока нет — значит, и пунктов нет), месяцы —
  `month_id__in=11__12`, ЭГЗ — `system_id__in=1`. Поиск `q` ищет слово и в названии, и в описании, как портал
  (по «Моноблок» портал находил 65 пунктов «Компьютер» с моноблоком в описании), поэтому фильтр по названию не нужен.
- Статуса «На проверке камерального контроля» в zakup нет; фильтр по названию статуса просто его не встречает.
- Карточка пункта содержит всё, что робот брал с портала: БИН, код и название ЕНС ТРУ, описания, дату и номер акта,
  единицу измерения, место поставки.
- **Нет номера исходного пункта** у изменённых пунктов (`root` пустой). Портал отдавал его как «№ пункта плана», и
  по нему изменённая версия находила старую сделку (в выгрузке панелей 17 из 64 строк — такие версии).
- **Старые версии остаются «Утвержден».** Пример: сделка 46147 — пункт 80758527 (47 шт, 14,1 млн) и его замена
  88607772 (42 шт, 12,13 млн), оба «Утвержден». Поиск `q=80758527` возвращает только 88607772: `q` находит и
  более поздние версии пункта.
- У одного номера бывает несколько записей с разными статусами (88548598: «Утвержден» и «Проект договора»).

## Решение

- `src/kz/zakupGzPlanCollector.ts` — `collectGzPlansFromZakup` возвращает то же, что `collectGzPlans`, поэтому
  выгрузка, реестр заказчиков (контакты по-прежнему с портала) и запись в Bitrix не меняются. «№ пункта плана» равен
  номеру пункта, ссылка на пункт — `https://zakup.gov.kz/plan-items/<id>`, ссылка на заказчика — из реестра.
- `config/gz-plans.json`, `config/gz-plans.pk.json`: `"source": "zakup"`, `"zakupMinPlanPointId": 88654474`. Без
  `source` остаётся поиск портала (другие потребители не затронуты).
- Защита от дублей и откатов:
  1. **Только пункты новее реестра портала** (`zakupMinPlanPointId`). Пункты до 88654473 портал показывал, и связь
     их версий со сделками знал только он: часть сделок июня (38721, 38815, 34883…) без БИН и кода, найти их можно
     лишь по номеру исходного пункта. Без порога zakup завёл бы 88421396, 88160601, 88075650, 88112020, 88459798 —
     у портала это были версии сделок 38815, 38721, 40683, 41531, 38757.
  2. **Устаревшие версии отбрасываются:** если `q=<номер>` показывает более поздний пункт того же заказчика, пункт
     не берётся.
  3. **Связь новой версии со сделкой** (`src/bitrix/gzZakupRevisionLink.ts`, вызов в `bitrix-push-gz-deals.mts`):
     для пункта zakup без сделки ищем сделки того же БИН и кода ЕНС ТРУ и спрашиваем zakup `q=<№ пункта плана
     сделки>` и `q=<номер пункта сделки>`; если zakup показал там наш пункт — это дубль `plan revision` (сумма
     обновляется прежней логикой правок). Если zakup не знает ни одного номера сделки, версией считается сделка с той
     же плановой суммой (`plan revision (same amount)`: 88182883, 9 ноутбуков на 4 230 000 ₸ = сделка 42927).
     Сбой проверки откладывает строку до следующего прогона.
  4. **Сумму меняет только самый новый пункт** (`findOutdatedRevisionIndexes`), если к одной сделке в прогоне ведут
     несколько пунктов.
  5. Пункт с несколькими записями zakup разных статусов не заводится.

(11 новых, из них 88182883 — дубль сделки 42927; правка 80758527 откатила бы сделку 46147) и 41 строка панелей

## Запись в Bitrix до слияния

По просьбе пользователя («можешь пока закинуть новые сделки») 18.11 с Mac записаны только новые сделки по пунктам
новее 88654473, без правок сумм: 57865–57889 (13) и 57901, 57903, 57905. Пользователь удалил 57873 («Устройство
компьютерное», 1 шт на 520 000 ₸) — отсюда правило ПК по коду, после него этот пункт отсеивается.

## Известные пробелы

- Семь старых пунктов (88623873, 88621515, 88594776, 88428896, 88628778, 88654201, 88629017) портал не показывал,
  сделок по ним нет, но из-за порога zakup их не берёт: проверить, не версии ли они сделок июня, нельзя.
- Контакты заказчиков по-прежнему берутся из реестра участников портала; если портал недоступен, строки новых
  заказчиков пропускаются с записью `registry` в отчёте сбора, как и раньше.
- Монитор публикаций (`kz-monitor-gz-published`) по-прежнему читает реестр портала.
