# Кейс в цифрах: сделки робота в Bitrix24

Цель: одной командой получить цифры для продаж — сколько сделок завёл робот, сколько выиграно,
на какую сумму и сколько ручной работы это заменило.

```bash
npm run bitrix:gz-case-stats -- --minutes-per-deal 10
```

Скрипт только читает (`ReadOnlyBitrixClient`, `crm.deal.list`), пишет `runs/gz-case/<дата>.md` и `.json`.

## Решения

- **Чья сделка.** Сделка робота — по `ORIGINATOR_ID`: `scrape2lead-gz-plans`, `scrape2lead-gz-lots`,
  `scrape2lead-procurement`. Первые сделки шли через Excel-импорт Bitrix (`app_iu_xls_import`), у них есть
  только название `[GZ …]` — считаются отдельной строкой «Ранний Excel-импорт», чтобы её можно было исключить.
- **Выиграно** — два независимых счёта: этап Bitrix (`STAGE_SEMANTIC_ID = S`, ставит менеджер) и итог с портала
  (`UF_CRM_S2L_GZ_OUTCOME`, префикс `won:`/`partner:`/`lost:`, пишет `deal-outcomes`). Итог с портала есть только
  у сделок, которые были открыты, когда работал `deal-outcomes`.
- **Сумма** — поле `OPPORTUNITY` сделки, то есть плановая сумма закупки, а не сумма подписанного договора.
- **Часы** — оценка: число сделок × `--minutes-per-deal` (по умолчанию 10). Замеров «до робота» в данных нет;
  цифру минут нужно взять у менеджеров.

## Уточнение после первого прогона (30.10.2026)

Первый прогон на живом Bitrix показал, где отчёт завышает или смешивает цифры:

- **«Ранний Excel-импорт» — не робот.** 16 сделок с `[GZ …]` в названии и пустым `ORIGINATOR_ID` завели вручную восемь
  менеджеров через веб-форму (июль–октябрь), у каждой есть сделка робота с тем же номером. Сделок `app_iu_xls_import`
  с `[GZ` в названии в Bitrix нет. Теперь `excel` — только `ORIGINATOR_ID = app_iu_xls_import` и название `[GZ`;
  остальные сделки с `[GZ` идут отдельной строкой «Ручные копии сделок робота» и в итог не входят.
- **Одна закупка — две сделки.** Робот заводит сделку на пункт плана, а позже на лот по этому пункту. Лот считается
  повтором, если число до дефиса в номере лота (`ORIGIN_ID` `gz-lot:<N>-…` или название `[GZ лот <N>-…]`) совпадает
  с номером пункта у сделки-плана (`planRootsOf`: «ID Плана», `[GZ <N>]`, `gz-plan:<N>`). Отчёт показывает
  «Уникальных закупок (оценка)». На 30.10.2026 так совпали 391 из 1 523 лотов.
- **«Проиграно или закрыто» смешивало проигрыш и отсев.** Этапы с семантикой `apology` («Не проходим по ТХ», «Сумма не
  соответствует минимальной», «Дубль», «Закупка состоялась»…) — это отсев менеджером, `failure` — проигрыш. Скрипт берёт
  семантику этапов из `crm.status.list` по воронкам, где лежат сделки. Доля выигранных теперь двумя строками: среди
  выигранных и проигранных и среди всех закрытых.
- **Итоги портала показывались не все.** Четыре строки давали 3 859 из 4 206. Теперь выводятся и `published`,
  `contract-draft`, `failed`, `cancelled`, `terminated`, `repurposed`, а неизвестные виды — строкой «Другой итог».
  Для `won` выводится сумма, плюс строка «Выиграно всего (этап Bitrix или портал)» без повторов.

RED: 6 новых тестов в `tests/bitrix/gzCaseStats.test.ts` (ручные копии, лоты-повторы, отсев, выигранные по порталу,
текст отчёта). GREEN: 13 тестов; формулировка доли в старом тесте обновлена.

## Выигранные по источнику

Строка «Выиграно всего» делится по источнику (`wonBySource`).

Первый вариант подписывал выигрыш из пункта плана «робот нашёл закупку до объявления». Это не подтверждено: скрипт
не сравнивает дату сделки с датой объявления, а 48 из 85 выигранных на 30.10.2026 — в воронке «Электронный магазин»,
где обычного объявления нет. Пометка убрана.

Прогон показал и вторую ловушку: все 85 выигранных — из планов, потому что `deal-outcomes` проверяет только
`scrape2lead-gz-plans`, а сделки по лотам менеджеры почти не закрывают (1 519 из 1 523 открыты). Поэтому у каждого
источника печатается покрытие (`coverageBySource`): у скольких сделок есть итог с портала и сколько закрыто в Bitrix.
Если итогов с портала у источника нет, отчёт пишет, что ноль выигранных там — «нет данных», а не «не выиграно».

Дату объявления можно взять из `UF_CRM_S2L_GZ_PUBLISHED_AT`, но там время, когда робот заметил объявление, а не дата
публикации; для «Электронного магазина» её нет. Пока не используется.

RED: тесты «делит выигранные по источнику и показывает, отслеживаются ли там итоги» и «не выдаёт ноль выигранных за
результат». GREEN: 15 тестов.
