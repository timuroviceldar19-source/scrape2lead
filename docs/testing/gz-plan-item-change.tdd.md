# Смена товара в пункте плана: журнал TDD

## Проблема
Сделка 48115 (пункт плана 88137237) заведена 06.10 с кодом ЕНС ТРУ 262030.100.000043 «Доска специальная». 15.10 заказчик заменил товар на 279020.100.000002 «Панель жидкокристаллическая», сумма (1 200 000) и количество (1) остались прежними. На портале номер пункта тот же, в реестре запись новая (id 88294659, `rootrecordId` 88137237), старой нет. Менеджер увидел расхождение: в плане один код, в карточке другой.

Причина: `src/bitrix/gzPlanRevision.ts` считает пункт изменённым, только если поменялись сумма или количество, и обновляет только их. Смену товара робот не замечал.

Замер на живых данных (16.10.2026, только чтение): открытых сделок по плану 971; реестр отдаёт действующую версию по 403; из них у 61 код в Bitrix не совпадает с текущим (после отсева записей, которые только совпали по номеру); 50 отсеяно проверками; 568 в индексе API нет.

## Решение
- `src/kz/goszakupPlanItems.ts`: действующая версия пункта по номеру на портале (`rootrecordId`): активная, не удалённая, с наибольшим id; пачки по 100; сбой пачки не останавливает остальные.
- `src/bitrix/gzPlanItemChange.ts`: чистая сверка. Меняет «Код ЕНСТРУ», «Код ТРУ», «Наименование», «Название ЕНСТРУ»; название сделки и строку `Item:` в комментарии, только если они ещё в виде, в котором их написал робот; готовит комментарий «План изменён заказчиком». Проверки против записей, которые только совпали по номеру: БИН сделки (поле или `BIN:` в комментарии) равен БИНу пункта, версия не старше сделки, год не раньше года сделки.
- `scripts/bitrix-sync-gz-plan-items.mts`: просмотр по умолчанию, `--execute`, пробно `--limit 5`; запись без записи в живую ленту (`REGISTER_SONET_EVENT: N`), потом комментарий в ленту сделки. Повторный запуск ничего не пишет: после правки код совпадает.
- Ежедневно: шаг «Sync plan item changes» в job `deal-outcomes` (`gz-daily-pk.yml`, утренний слот), `if: always()`.
- Сумму и количество по-прежнему ведёт `gzPlanRevision`; здесь они не трогаются.

## Срез 3: старые сделки, где `ORIGIN_ID` не равен номеру пункта (19.10.2026)

Менеджер написала в чате сделки 40443: в карточке «Панель интерактивная» (262030.100.000021), в реестре 279020.100.000002. Скрипт эту сделку не поправил: у неё `ORIGIN_ID` = `gz-plan:4804795` (внутренний номер записи на портале, он же последняя часть ссылки на пункт), а номер пункта 81584546 лежит в «ID Плана» и в названии. Скрипт брал номер только из `ORIGIN_ID`, искал в реестре запись 4804795 и считал, что пункта там нет.

- `planRootsOf(deal)`: все номера, под которыми сделка знает свой пункт: «ID Плана», второе поле номера, `[GZ <номер>]` из названия, `ORIGIN_ID`. Реестр запрашивается по всем.
- `planItemSync` берёт первую запись реестра, прошедшую проверки (БИН, версия не старше сделки): номер из `ORIGIN_ID` может совпасть с чужой записью.
- Живой просмотр: к правке ещё 16 сделок (в том числе 40443); 42 отсеяно (у 37 в карточке нет кода товара, у 5 не совпал БИН, это совпадения номеров); 551 нет в индексе реестра, их по-прежнему проверить нельзя.

RED: 4 теста падали, затем зелёные; `npm run lint` чистый.
