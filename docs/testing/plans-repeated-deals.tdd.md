# Один пункт плана — одна сделка в мониторе

## Границы

Этап 3а. Ветка создана от свежего `origin/main` после слияния PR #111.
Меняется только чтение данных монитора планов. Bitrix, Рынок, workflow и
нормализация уникальных старых сделок без кода и количества не меняются.
Тестовые имена, номера и значения вымышлены; рабочих данных в журнале нет.

## Проверка вызовов до реализации

`isPlanDeal` в `plans/collect.ts` вызывается нормализатором и при отборе
исходных строк сборщика. Он остаётся без изменений: принадлежность к планам
не зависит от стадии CRM. Одноимённая локальная функция в `gzPlanItemChange.ts`
относится к другому сценарию и также не меняется.

Правило стадий сверено с `salesPult/collect.ts` (проверка исходов) и
`reporting/model.ts`: исключаются стадии, содержащие `DUPLICATE` или `DOUBLE`.

## RED

Сначала добавлен `tests/bitrix/salesPultPlansRepeatedDeals.test.ts`.
До изменения реализации все 13 проверок упали: отсутствовала экспортируемая
дедупликация, стадии дублей попадали в агрегаты, повторные пункты учитывались
несколько раз. Затем внесены изменения реализации.

## Решения

1. После отбора планов отдельный шаг исключает стадии с `DUPLICATE`/`DOUBLE`
   без учёта регистра. Этот шаг выполняется до нормализации и дедупликации;
   исключённая выигранная сделка не может вытеснить действующий план.
2. Чистая экспортируемая `dedupePlanDeals` принимает общий список
   нормализованных сделок ИП и КТ. Ключ — непустой `planNumber` (rootrecordId),
   а не `ORIGIN_ID` версии пункта, группа или номер сделки.
3. Выбор из повторов лексикографический: `outcomeCategory === "won"`, затем
   `isOpen`, затем наличие непустого кода ТРУ, затем больший числовой ID.
   Для строковых ID используется числовое сравнение без преобразования в
   потенциально неточный JavaScript Number. При полном равенстве остаётся первая.
4. Пустые номера не объединяются. Позиция первого появления пункта сохраняется
   при замене победителем. Возвращается новый массив; входные записи не меняются.
   Уникальные записи возвращаются теми же объектами, без исправления полей.
5. Сборщик передаёт один очищенный список в `enrichManagerNames` и
   `buildPlansMonitorView`. Ненужные имена исключённых владельцев не запрашиваются.
   Итоги, месяцы, менеджеры, заказчики, способы и `openPlans` получают одинаковый
   набор сделок. Лог «вне групп» не включает отсеянные стадии и повторы.
6. Новые логи содержат только количества: `[Планы] на стадии «Дубль»: N`
   и `[Планы] повторов: N`. Число повторов — число удалённых записей после
   исключения стадий, а не число ключей с повторами. Суммы и рабочие данные
   в лог не добавляются.

## GREEN

Профильный прогон: 53 теста прошли (13 новых и 40 существующих проверок монитора,
включая Chromium). `npm run lint` прошёл. Полный набор: 1844 теста прошли,
4 пропущены. Для независимого PDF-теста использовано временное Python-окружение
с ReportLab вне репозитория.

Новые тесты проверяют каждый приоритет независимо от порядка входных записей,
числовой порядок ID, выигранный исход закрытой сделки, повтор между группами,
различие номера пункта и номера версии, пустые номера, чистоту функции,
сохранение порядка и уникальных старых записей, разные написания стадий дублей,
единый набор во всех срезах и загрузку имён только оставшихся менеджеров.
